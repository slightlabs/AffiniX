# Spike: io_uring backend (M8-01/02/03)

Date: 2026-09-20. Host: kernel 7.0.0-31-generic, GCC 15.

## What was built

`UringBackend` (`include/afx/backend/uring.hpp`, `src/backend/uring.cpp`)
implements the `IoBackend` concept natively: the kernel performs the I/O and
completions arrive through the CQ ring — no readiness emulation. It is built
directly on the io_uring syscall ABI (`io_uring_setup` / `io_uring_enter` /
`io_uring_register`) rather than liburing: the ABI is stable, the ring code is
~150 lines, and no external dependency enters the build (§23). If that
judgment ages badly, liburing can replace the internals without touching the
backend API.

- **M8-01 setup/batching/drain:** `submit_*` stage SQEs into the shared SQ
  ring (no syscall); `wait()` publishes the batch and issues a single
  `io_uring_enter` — submit + wait-for-1-completion in one syscall, with the
  deadline carried by `IORING_ENTER_EXT_ARG`. CQEs drain into
  `std::span<Completion>` with `More` mapping to `CompletionFlag::More`.
  On a full SQ the staged batch is submitted and the alloc retried once;
  `Err::Full` is the backpressure answer after that.
- **M8-02 probe + fallback:** `UringBackend::probe()` wraps
  `IORING_REGISTER_PROBE`; `AutoBackend` checks every opcode it issues
  (POLL_ADD, POLL_REMOVE, SENDMSG, RECV, SEND, ACCEPT, CONNECT,
  ASYNC_CANCEL) before committing, and otherwise stays on epoll. Ring
  creation is two-phase (`create()` returns `Result`) so setup failure is a
  value, not an exception or a half-built object.
- **watch:** `IORING_OP_POLL_ADD` with `IORING_POLL_ADD_MULTI` gives
  persistent readiness CQEs that map cleanly onto `Interest`. `modify` is
  POLL_REMOVE + POLL_ADD with the old request's terminal `-ECANCELED` CQE
  swallowed, so a successful modify never delivers a spurious error to a
  live sink. Re-`attach` on an already-watched fd retires the stale poll
  first.
- **wake:** an eventfd under a multishot poll; `wake()` is an eventfd write,
  and the drain resets the counter.

## Traps found (worth keeping in the notes)

1. `io_uring_register(fd, IORING_REGISTER_PBUF_RING, &reg, n)` wants
   `n = 1`; `0` is EINVAL.
2. `IORING_OP_CONNECT` takes `addrlen` in `sqe->off` (`addr2`), not `len`.
3. The app-allocated pbuf-ring mode (anonymous mmap + `ring_addr`) is the
   right default; `IOU_PBUF_RING_MMAP` (kernel-allocated, mmap after
   register) is the alternative.
4. `Completion` translation must translate the poll mask to the
   `ReadyRead/ReadyWrite/ReadyErr/ReadyHangup` vocabulary, not pass the raw
   `POLL*` bits through.

## Open question 4 — does the concept fit provided-buffer rings?

Verdict: **it fits, but only with a copy — which mostly defeats the point.**

`submit_recv(u, fd, MutByteSpan buf)` promises the bytes land in the
caller's buffer at completion time. With `IOSQE_BUFFER_SELECT` the kernel
chooses a buffer from the registered ring, so the backend must `memcpy`
into `buf` before emitting the completion and then re-provide the buffer.
That is implemented behind `UringConfig::use_pbuf_ring` and passes the same
tests as the direct path — the concept survives unchanged.

But the copy means the two wins are limited:

- Provided buffers still help **memory footprint** — connections can keep a
  small `MutByteSpan` while the kernel pool absorbs large bursts — at the
  cost of one userspace copy per recv.
- True zero-copy recv needs a *different* contract: a `Completion` that
  hands the sink a borrowed buffer + a return token (handle again, §26.3).
  That is a concept extension, not a backend detail, and should be decided
  with the M8-10 epoll-vs-uring benchmark rather than speculatively. If
  benchmarks show the copy is cheap (it is one `memcpy` per recv, on top of
  the kernel copy either path already pays), keep the copy and the frozen
  concept; if buffer memory dominates at 100k connections, add a
  `RecvOwned` completion variant.

Registered buffers (`IORING_REGISTER_BUFFERS`, `READ_FIXED`/`WRITE_FIXED`)
were not pursued: they pin memory for files, and for sockets the provided-
buffer ring is the mechanism that matters.

## Deferred to later M8 tasks

Multishot accept landed (M8-04): `IORING_ACCEPT_MULTISHOT` in `sqe->ioprio`,
one submit keeps firing, the caller gates re-arming on `CompletionFlag::More`,
and double-arming the same tag is refused. Multishot **recv** is deferred:
`IORING_RECV_MULTISHOT` requires buffer-select, and under the caller-owned
`MutByteSpan` contract two recv CQEs draining in one batch would memcpy into
the same destination before dispatch sees them — that is the borrowed-buffer
contract question again, to be decided with M8-10. `MSG_RING` wake, SQPOLL,
`SO_TIMESTAMPING` plumbing, and the backend-parity suite remain. CQ overflow
is not yet handled defensively (completions beyond the CQ size are dropped by
the kernel with only an overflow flag) — worth a counter and a sizing rule
before M8 exit.
